# 5.49 · v0.52：删题不级联图片、回收站不存图片（修复）

> 本文件是 [v0.51](v0.51.md) 之后的增量。这是一个修 bug 的版本，没有新增功能。

## 5.49.1 问题

清空试用数据时发现的：`POST /api/mistakes/batch-delete` 删掉 9 道题、回收站再 purge 之后，
`mistake_images` 里还留着 4 条指向已不存在题目的行。查下去是三个地方凑成了一个互相掩盖的 bug：

| # | 问题 | 后果 |
|---|---|---|
| 1 | `delete_mistake()` / `delete_mistakes()` 只 `DELETE FROM mistakes` + `DELETE FROM review_logs` | 图片关联行变成孤儿，库越删越脏；且没有任何清理入口 |
| 2 | `_snapshot_for_trash()` 只存 `mistakes` 行与复习日志，`trash` 表根本没有图片列 | 如果只补第 1 条，删题再恢复就会**丢图** |
| 3 | `restore_trash()` 不重建 `mistake_images` | 图片能回来纯属「第 1 条没做」的副作用 —— 一修第 1 条就暴露 |

顺带发现同一条链路上还有第二个漏水点：v0.51 刚加的留证字段
（`student_answer` / `hints` / `judgement`）和更早的 `step`，
`_snapshot_for_trash()` 的 SELECT 里都没有、`restore_trash()` 的 INSERT 里也没有。
也就是说**删一道题再从回收站恢复，诊断留证会静默清零** —— 恰好是 v0.51 花力气补上的那批数据。

## 5.49.2 改了什么

| 改动 | 位置 | 说明 |
|---|---|---|
| `trash` 加 `images` 列 | `app.py` 的 `SCHEMA` + `MIGRATIONS` | `images TEXT NOT NULL DEFAULT '[]'`，老库由 `init_db()` 自动 ALTER |
| `_snapshot_for_trash()` | `app.py` | 返回 `(row, logs, images)`；logs 的 SELECT 补 `step` / `student_answer` / `hints` / `judgement`，images 取 `{file, field}` |
| `_push_trash()` | `app.py` | INSERT 带上 `images` |
| `delete_mistake()` / `delete_mistakes()` | `app.py` | 补 `DELETE FROM mistake_images WHERE mistake_id = ?` |
| `restore_trash()` | `app.py` | 日志 INSERT 从 8 列扩到 12 列；按快照用 `_set_images()` 写回图片关联 |
| `list_trash()` | `app.py` | 返回项加 `image_count`，回收站列表能看出这条带几张图 |

### 为什么恢复时只在「快照里确实有图」才动 `mistake_images`

```
if images:
    _set_images(conn, target, [entry for entry in images if isinstance(entry, dict)])
```

迁移前入库的老回收站记录 `images` 是默认值 `'[]'`，而那时候删题**并没有**删图片行 ——
无条件 `_set_images(conn, target, [])` 会先把这些还在的关联清空，反而把老记录恢复坏。
所以空快照一律不动表：新记录删题时已经级联清干净了，没有残留需要清。

### 为什么删关联行但不删图片文件

图片文件是**内容寻址**存在 `data/images/` 的：同一张图被多道题引用时只有一个文件。
删掉某道题的关联行不影响别人；而按引用计数删文件需要全库扫描，且中途失败会留下半删状态。
库本身才几十 MB 级别，文件留着比删错便宜 —— 这也是这个项目一直没做图片 GC 的原因。
